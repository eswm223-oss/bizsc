# BizSC EDINET 書類棚卸し Phase

## 1. このドキュメントの目的

このPhaseでは、EDINETから取得できる書類のうち、

- 現在上場している企業
- 現在日から過去10年間の提出書類
- `csvFlag = "1"`

に該当する書類を棚卸しします。

このPhaseでは **CSV本体の大量ダウンロードはまだ行いません**。

目的は、

> 「現在上場している企業について、過去10年間にEDINET上でCSV取得対象となる書類が、どの書類種別で何件存在するのか」

を実データで把握することです。

棚卸し結果を確認した後、次PhaseでCSV本体の取得方法を設計します。

---

# 2. 今回確定した条件

## 2.1 対象企業

現在上場している企業を対象とします。

### 上場判定方法

ユーザー指定により、**証券コードを基準**に判定します。

ただし、重要な注意があります。

過去日の書類一覧APIに含まれる `secCode` が存在することだけを理由に、

```text
現在上場している
```

と判定してはいけません。

EDINET公式仕様では、提出書類一覧に含まれるEDINETコード及びそれに紐づく属性情報は、
レコード作成時点の情報であり、その後属性が変更されても過去の提出書類一覧は更新されません。

したがって、

```text
過去の書類一覧で secCode がある
=
現在も上場している
```

とは限りません。

このPhaseでは、**現在時点のEDINETコードリストを基準として現在の証券コード集合を作り、過去書類の `secCode` と照合する**方式を採用します。

### 現在上場企業集合の考え方

現在取得できる最新のEDINETコードリストを利用します。

EDINETコードリストには少なくとも以下の項目があります。

```text
EDINETコード
提出者種別
上場区分
連結の有無
資本金
決算日
提出者名
提出者名（英字）
提出者名（ヨミ）
所在地
提出者業種
証券コード
提出者法人番号
```

今回のユーザー指定では、上場判定の基準は **証券コード** とします。

したがって基本的には、

```text
現在のEDINETコードリスト
    ↓
証券コードが設定されている提出者
    ↓
現在対象とする証券コード集合
```

を作成します。

`上場区分` は今回の主判定条件にはしません。

ただし、検証・異常確認用の情報として参照して構いません。

### 証券コードの型

証券コードは数値として扱わず、**文字列として扱ってください**。

`int` へ変換しないでください。

---

## 2.2 対象期間

基準は、

> 現在日から過去10年間の提出日ベース

です。

実行時の現在日を `end_date` とし、

```text
start_date = end_date の10年前
end_date   = 実行時の現在日
```

とします。

期間の両端を対象に含めます。

### 重要

日付を固定値で実装しないでください。

実行日の現在日から動的に10年前を算出できる構造にしてください。

うるう日（2月29日）でも異常終了しないようにしてください。

---

## 2.3 取得対象

書類一覧APIの結果のうち、

```text
csvFlag == "1"
```

の書類をすべて棚卸し対象とします。

### 書類種別を先に限定しない

このPhaseでは、

```text
docTypeCode == "120"
```

など、特定の書類だけに絞り込んではいけません。

有価証券報告書だけでなく、

- 半期報告書
- 過去の四半期報告書
- 訂正書類
- 臨時報告書
- 有価証券届出書
- その他CSVが存在するEDINET提出書類

も含め、

**現在上場企業に紐づき、`csvFlag = "1"` のものをまず全部把握します。**

その後、`docTypeCode` ごとに集計します。

# 3. EDINET公式仕様上の重要事項

EDINET API Version 2を利用します。

公式資料:

```text
https://disclosure2dl.edinet-fsa.go.jp/guide/static/disclosure/WZEK0110.html
```

API仕様書:

```text
https://disclosure2dl.edinet-fsa.go.jp/guide/static/disclosure/download/ESE140206.pdf
```

## 書類一覧API

既存Phaseで実装済みの以下を利用します。

```text
GET https://api.edinet-fsa.go.jp/api/v2/documents.json
```

パラメータ:

```text
date=<YYYY-MM-DD>
type=2
Subscription-Key=<APIキー>
```

既存の

```python
fetch_document_list(target_date)
```

を可能な限り再利用してください。

---

## 3.1 `secCode`

書類一覧APIの

```text
secCode
```

は「提出者証券コード」です。

ただし前述のとおり、過去の書類一覧に含まれる提出者属性は、
後から現在値へ自動更新されるものではありません。

そのため、現在上場企業を判断するマスタとして
過去レスポンスの `secCode` 有無だけを使用してはいけません。

---

## 3.2 `csvFlag`

```text
csvFlag = "1"
```

は、その書類にCSVファイルが存在することを示します。

CSVはEDINET上のXBRLをCSV形式へ変換したファイルです。

書類取得APIでは `type=5` でCSVを取得できます。

ただし、このPhaseでは **type=5 を呼び出しません**。

CSVファイル本体はダウンロードしません。

---

## 3.3 `legalStatus`

棚卸し対象の各書類について、

```text
legalStatus
```

も必ず保持・集計してください。

値:

```text
"1" = 縦覧中
"2" = 延長期間中
"0" = 閲覧期間満了
```

このPhaseの主条件は `csvFlag = "1"` ですが、
次Phaseで「実際にダウンロード可能か」を判断するため、
`legalStatus` を捨ててはいけません。

---

## 3.4 `disclosureStatus`

不開示等の状態により、CSVが存在していても実際に取得できない可能性があります。

そのため、

```text
disclosureStatus
```

も棚卸しデータに保持してください。

このPhaseでは複雑な不開示判定ロジックを作らず、
まず値を保持・集計するだけにしてください。

---

# 4. 過去10年分取得時の注意

書類一覧APIは **1日単位** で取得します。

過去10年を全暦日で取得すると、
概ね3,650件以上のAPIリクエストになります。

したがって、いきなり10年分を一括実行してはいけません。

---

## 4.1 全暦日を対象とする

土日・祝日をコード上で勝手に除外しないでください。

「提出書類は平日だけ」と仮定せず、

```text
start_date ～ end_date
```

の全暦日を順番に対象とします。

---

## 4.2 並列アクセス禁止

EDINETへ多数のリクエストを同時送信しないでください。

以下は禁止です。

- asyncioによる大量並列取得
- ThreadPoolExecutorによる並列取得
- multiprocessingによる並列取得
- 複数コンテナからの同時取得

このPhaseでは **逐次処理** としてください。

---

## 4.3 429

EDINET APIから

```text
429 Too Many Requests
```

が返った場合、

- 無限リトライしない
- 高速に再試行しない
- 処理を安全に停止する
- どの日付まで完了したか分かるようにする

設計を優先してください。

---

## 4.4 途中再開

10年分は件数が多いため、
途中でネットワークエラーや429が起きても最初からやり直す必要がない設計を検討してください。

ただし、このPhaseではDBを作りません。

実装を複雑化させない範囲で、

- 処理済み日付
- 最終成功日
- 棚卸し結果

をローカルファイルとして保持する方式を候補とします。

実装前に保存形式と保存場所をユーザーへ提示してください。

勝手に大量データ用ディレクトリをGit管理対象へ追加しないでください。
