# BizSC Screening 設計方針（評価項目・採点ルール）

更新日: 2026-11-05  
状態: **設計方針を合意／実装は未着手**。本書のテーブル・カラム名・型・API仕様は初期案であり、実装前に確定する。

## 1. 目的と利用イメージ

利用者が任意の評価項目を選び、項目ごとに条件と条件達成時の配点を設定する。BizSCは銘柄ごとに条件を判定し、合計点数の高い順に企業一覧を出力する。

評価対象は、単純な数値比較（例: PER 15倍以下）に限定しない。たとえば、営業利益率が3期連続で上がっている、52週高値から30%以上下落した、売上高の複数年成長率など、**時系列や複数データに依存する評価**を含む。

J-Quantsのキャッシュ済み企業情報・日次株価・バリュエーション・財務サマリーを当初の情報源とし、既存キャッシュテーブルは変更せずに評価機能を追加する方向で検討する。

## 2. 今回決めた基本方針

1. 評価項目の共通メタデータと、利用者が保存する個別評価条件を分離する。
2. 初期案は **`screening_metric`（項目マスタ）、`screening_rule_set`（評価セット）、`screening_rule`（評価ルール）** の3テーブル。
3. 項目によって異なる設定値は `screening_rule.params` の **PostgreSQL `JSONB`** に保持する。項目ごとに専用カラムを増やさない。
4. JSONBの形は評価項目ごとに **Pydantic v2** で検証する。項目コードはサーバー側の定義済みマスタ／レジストリから選び、任意Pythonコードや文字列式を実行しない。
5. 評価指標の**算出**、条件の**判定**、条件達成時の**加点**、合計点の**ランキング**を分離する。
6. ここでの合意は設計方針についてであり、テーブル作成・API・画面・スコア計算処理は**未実装**。

## 3. 論理データモデル（案）

| テーブル | 役割 | 主なカラム候補 |
| --- | --- | --- |
| `screening_metric` | 利用できる評価項目の定義 | `code` (PK), `name`, `category`, `description` |
| `screening_rule_set` | 利用者が保存した評価セット | `id` (PK), `name` |
| `screening_rule` | 評価セット内の個別条件・配点 | `id` (PK), `rule_set_id` (FK), `metric_code` (FK), `params` (JSONB), `score` (整数の案), `enabled` (真偽値) |

関連: `screening_rule_set` **1 : N** `screening_rule`、`screening_metric` **1 : N** `screening_rule`。

項目マスタには評価項目コードを持たせ、設定内容とPython側の算出／判定処理の対応付けに利用する。具体的な主キー型、所有ユーザー、表示順、更新日時、削除方法、ルールのバージョン管理は実装時に判断する。

### 3.1 JSONBの例（仕様の確定ではない）

営業利益率が3回連続で上昇した場合に30点:

```json
{
  "metric_code": "operating_margin_streak",
  "params": { "period": "annual", "count": 3 },
  "score": 30
}
```

52週高値から30%以上下落した場合に40点:

```json
{
  "metric_code": "price_drawdown",
  "params": { "lookback": "52w", "threshold_pct": 30 },
  "score": 40
}
```

売上高の過去5年CAGRが10%以上の場合に20点:

```json
{
  "metric_code": "sales_cagr",
  "params": { "years": 5, "operator": "gte", "threshold_pct": 10 },
  "score": 20
}
```

上記の `metric_code` と各パラメータは**例示名**。連続上昇の「3期」が「3回の増加」を意味するなら、比較対象の決算数は4期必要になる点に留意する。

### 3.2 入力検証（案）

Pydanticモデルを評価項目コードに対応付け、JSONB保存前と読出し後の両方で検証する。例えば、`count` は正の整数、`threshold_pct` は許容範囲内の数値、`lookback` は許可された期間のいずれか、といった制約を付ける。

将来パラメータ仕様を変更する場合、既存保存データとの互換性を確保するため、必要に応じてルール定義のバージョンを導入する。

## 4. 処理責務（案）

```text
J-Quantsキャッシュ（既存）
    ↓
銘柄別の必要データ取得・集約
    ↓
指標算出（例: 52週高値、営業利益率の期別推移）
    ↓
条件判定（例: 30%以上下落、3期連続上昇）
    ↓
配点加算（条件を満たす場合のみ）
    ↓
企業別の合計点・条件別内訳
    ↓
合計点の降順でランキング表示
```

初期実装はDBから必要なデータをまとめて取得し、Pythonサービス側で算出・採点する方向を想定する。データ量・応答時間を確認した後、必要に応じて指標の事前集計やSQL側への移管を検討する。

## 5. 未決定事項

- **欠損値の扱い:** 欠損と条件不達を区別したうえで、無得点／評価不能／除外のどれを採用するか。
- **集計対象期間と基準日:** 期末実績・株価の基準日、決算訂正、株価調整の扱い。
- **必須条件:** 加点以外に「対象外にするフィルタ」を設けるか。
- **複数段階配点・条件の結合:** 同一項目の段階評価、AND/OR、自由な式定義を許可するか。
- **保存と実行:** ルール編集画面、評価セットの複製、実行結果履歴、スコア内訳、ページングの具体仕様。
- **実装範囲:** J-Quants保存データで実際に計算可能な指標の一覧と優先順位。
